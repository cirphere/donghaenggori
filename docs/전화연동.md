# 전화 연동 (ClawOps VoiceML)

## 왜 AI Voice Agent 를 쓰지 않았나

ClawOps 에는 두 경로가 있다.

| | AI Voice Agent SDK | **VoiceML (선택)** |
|---|---|---|
| 방식 | OpenAI/Gemini Realtime 이 통화를 주도 | 우리가 XML 로 통화 흐름을 지시 |
| LLM | 세션 필수 (`session=` 에 None 불가) | 없음 |
| 어르신 발화 | 외부 LLM 으로 전송 | ClawOps 전사만 |

Agent SDK 를 쓰면 **우리 긴급 분류기가 모든 발화를 보지 못한다.** LLM 이 도구를
불러줄 때만 안전장치가 돈다 — LLM 이 "가슴이 답답하다"를 잡담으로 판단하고
넘어가면 그대로 지나간다. 재현율 0.993 을 만들어 놓고 그 앞에 판정자를 하나 더
세우는 셈이다. 민감한 건강 발화가 외부 LLM 으로 나가는 문제도 있다.

그래서 **AI 는 인사만 하고 그다음은 듣기만 한다.** 이 서비스의 원칙("AI 는
대화하지 않는다, 응급 여부를 판단하지 않는다")과 구현이 같아진다.

## ClawOps 에 등록할 주소

| 항목 | 값 |
|---|---|
| **수신 웹훅** | `https://donghaenggori.dohyeongops.com/api/voice/incoming` |
| **통화 상태 webhook URL** | `https://donghaenggori.dohyeongops.com/api/voice/status` |

**한 번호는 웹훅을 하나만 가진다.** 같은 번호를 다른 앱과 나눠 쓸 수 없다 —
누가 그 번호를 쓸지 팀에서 먼저 정해야 한다.

나머지 주소(녹음 콜백·확인 콜백·전환 결과)는 **우리가 VoiceML 안에 넣어 보낸다.**
대시보드에 따로 적을 필요가 없다.

    <Record action=".../api/voice/recording">    1턴 녹음 끝
            action=".../api/voice/confirm">      2턴 답변 끝
    <Dial   action=".../api/voice/dial-result">  긴급 전환 끝

### 통화 상태 웹훅에서 켤 이벤트

대시보드의 '받을 이벤트' 중 **호전환 결과**가 핵심이다.

> 전환 시작·연결·성공·실패를 실시간으로. 통화가 끝날 때까지 기다리지 않아도 됩니다

`<Dial action>` 은 전환이 **끝나야** 오지만 이쪽은 실시간이고, action 콜백이
어떤 이유로 우리에게 닿지 못해도 백업이 된다. 담당자가 못 받은 것을 아무도
모르는 상태만은 피해야 하므로 둘 다 받는다.

나머지(발신 시작·벨 울림·응답·종료)는 켜도 되고 꺼도 된다 — 우리는 감사
로그에만 남긴다. 이 엔드포인트는 통화를 지시하지 않고 204 로 끝낸다.

## 긴급 전환 결과를 반드시 받는다

담당자가 못 받은 것을 **아무도 모르는 상태**가 제일 위험하다. 어르신은
"연결하지 못했습니다" 안내를 듣고 끊는데, 시스템에 기록이 없으면 아무도 다시
걸지 않는다.

`<Dial action>` 으로 결과를 돌려받아 접수에 남기고 감사 로그에 기록한다.

| DialCallStatus | 우리 표기 | 동작 |
|---|---|---|
| completed | 연결됨 | 조용히 종료 |
| busy / no-answer / failed / canceled | 통화중 / 응답없음 / 실패 / 취소됨 | 119 안내 + 접수에 표시 |

사회복지사 콘솔의 접수 목록에 `전환 응답없음` 뱃지가 붙고, 상세 팝업에는
"담당자와 연결되지 않았습니다 — 다시 연락 필요"가 뜬다.

## 흐름

**본인 확인을 통화 앞에서 먼저 한다.**

```
전화 수신
  → POST /api/voice/incoming
      <Say> 동행고리입니다. 박순자 님 맞으신가요?
            맞으시면 1번, 아니시면 2번을 눌러 주세요. </Say>
      <Gather numDigits=1 timeout=7 action=/identity/>
      <Say> 어디가 편찮으신지… </Say>     ← 키를 못 눌렀을 때 여기로 흘러간다
      <Record action=/recording?who=unknown>

  → POST /api/voice/identity
      1번 → <Say> 어디가 편찮으신지… </Say> <Record ?who=self>
      2번 → <Say> 성함과 읍면동, 병원과 날짜… </Say> <Record ?who=other>

  → POST /api/voice/recording?who=…      ※ 어르신은 아직 통화 중
      내려받기 → STT → 파이프라인
        긴급   <Dial> 담당자
        평상시 <Say> 접수했습니다 → <Hangup/>
```

### 왜 앞에서 묻나

예전에는 녹음을 먼저 받고 **STT 를 마친 뒤에** 되물었다. 그 대기 사이에 통화가
끊겨 확인 질문이 아예 들리지 않았다 — 우리 로그에는 200 으로 찍혔는데 그때는
이미 통화가 끝난 뒤였다.

확인을 앞으로 옮기면 **STT 대기가 통화 맨 끝(접수 안내)으로 밀린다.** 거기서
잘려도 접수는 이미 저장돼 있어 잃는 것이 없다.

### `<Say>` 는 `<Gather>` **밖에** 둔다

문서 예제는 `<Gather>` 안에 `<Say>` 를 넣는 형식이지만, 실통화에서 **그 문구가
재생되지 않았다.** 어르신에게는 곧바로 뒤의 "어디가 편찮으신지" 만 들렸고
로그에도 `/identity` 가 찍히지 않았다. 밖에 두면 재생이 보장된다.

대신 문구 재생 중에 미리 누르는 것(barge-in)은 안 될 수 있다. 이 회선은
어차피 DTMF 가 안 먹는 것으로 보여 잃을 것이 없다.

### 키를 못 눌러도 된다

회선이 DTMF 를 전달하지 않는 것으로 보인다(`<Record finishOnKey>` 로 확인).
`<Gather>` 는 입력이 없으면 콜백 없이 끝나고, 뒤따르는 `<Say>`·`<Record>` 로
흘러간다. 그때는 `who=unknown` 이 되어 대상자가 `확인 필요` 로 남을 뿐,
접수는 그대로 만들어진다.

### 누른 번호는 '확인됨' 이 아니다

| 입력 | `identity_status` |
|---|---|
| 1번 | `추정` |
| 2번 | `확인 필요` |
| 무입력 | `확인 필요` |

**버튼을 눌렀다는 것이 본인이라는 증거는 아니다.** 남의 폰으로 건 사람도 1번을
누른다. 최대 `추정` 이고 확정은 사회복지사가 한다.

### 안내 멘트에 119 를 넣지 않는다

접수 전화에 대고 끊으라고 하는 것이 어색하고, 안내가 길어지면 어르신이 끝까지
듣지 않는다. 긴급은 발화에서 감지해 담당자로 넘기고, **전환이 실패했을 때만**
119 를 안내한다.

## 수신이다, 발신이 아니다

우리가 거는 게 아니라 **어르신이 우리 070 번호로 걸면** ClawOps 가 우리를 부른다.

```
어르신 → 070 번호 → ClawOps → POST /api/voice/incoming
                                 Direction=inbound
                                 From=010...   (어르신 번호 → 케어 프로필 조회)
                                 To=070...     (우리 ClawOps 번호)
                              ← VoiceML XML (우리가 통화 흐름을 지시)
```

문서 표현 그대로: *"platform sends an HTTP request to the configured webhook URL.
The server responds with VoiceML (XML) to control the call flow."*

`client.calls.create(url=...)` 예시는 **발신**(우리가 거는 경우)이라 여기서는
쓰지 않는다. 수신은 번호에 웹훅 주소를 등록해두면 ClawOps 가 알아서 호출한다.

## 설정

`.env` 에 넣는다. 값은 대시보드에서 가져온다.

```
CLAWOPS_SIGNING_KEY=        # Settings > Webhook 의 Signing Key (API Key 와 다름)
CLAWOPS_STAFF_NUMBER=       # 긴급 시 연결할 담당자 번호
CLAWOPS_MAX_RECORD_SECONDS=30
```

ClawOps 번호 설정에서 수신 웹훅을 이렇게 지정한다.

```
https://donghaenggori.dohyeongops.com/api/voice/incoming
```

**반드시 https 다.** 2턴 콜백 주소는 서버가 만들어 VoiceML 에 넣는데, 그
주소가 http 로 나가면 Cloudflare 가 301 로 돌리면서 POST 본문이 날아가
확인 단계가 통째로 깨진다. `.env` 의 `PUBLIC_BASE_URL` 에 공개 주소를
적어두면 헤더 추정에 기대지 않고 확실해진다.

    PUBLIC_BASE_URL=https://donghaenggori.dohyeongops.com

※ 대시보드에서 이 항목을 뭐라고 부르는지(Voice URL / 수신 웹훅 등)는 문서에
없다. Twilio 의 "A CALL COMES IN → Webhook" 에 해당하는 자리다. 번호 담당자에게
확인할 것.

**서명 키를 반드시 등록한다.** 이 엔드포인트는 인터넷에 열려 있어야 하므로,
키가 없으면 주소를 아는 누구나 접수를 만들 수 있다. 키가 비어 있으면 서버가
503 으로 거절한다 — 열어둔 채 조용히 통과시키지 않는다.

## ⚠ Cloudflare Access 와 충돌한다

사회복지사 콘솔을 지키려고 호스트 전체에 Access 를 걸면 **ClawOps 웹훅도 막힌다.**
ClawOps 는 브라우저가 아니라 로그인 화면을 통과하지 못한다. 전화가 걸려와도
우리 서버까지 오지 않는다.

회선을 붙일 때는 `/api/voice/` 만 예외로 뺀다.

> Zero Trust → Access → Applications → **Add an application** (하나 더)
> Application domain: `donghaenggori.dohyeongops.com`  **Path: `/api/voice`**
> Policy: **Bypass — Everyone**
>
> Access 는 더 구체적인 경로 정책을 먼저 적용하므로, 전체 정책보다 이 정책이
> 우선한다. 순서가 헷갈리면 이 경로 정책을 목록 위로 올린다.

열어두는 것이 불안해 보이지만, 이 경로는 **서명 검증이 지킨다** — 서명이 없거나
틀리면 401, 키가 미설정이면 503 이다(tests/test_voice.py 에서 회귀로 잡는다).

확인:

```bash
# 서명 없이 호출 → 401 이어야 한다. 302(로그인 리다이렉트)면 Access 가 아직 막고 있다.
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://<우리 도메인>/api/voice/incoming -d 'From=010-0000-0000'
```

## 확인

회선 없이 웹훅을 흉내내 검증한다. CI 에서도 돈다.

```bash
python -m tests.test_voice
```

검사 항목: 서명 없음·틀림 거절 / 인사→녹음 XML / 문답(`<Gather>`) 없음 /
긴급 시 통화 중 `<Dial>` / 평상시 안내 후 종료 / 빈 녹음이면 접수 안 만듦 /
키 미설정이면 503.

## 어르신이 "끊으면 되나요"

**끊으면 안 된다.** `<Record>` 에는 침묵 감지가 없다 — 문서에 있는 속성은
`maxLength` · `finishOnKey` · `playBeep` · `action` 뿐이다. 말을 마쳐도 저절로
끝나지 않으므로 녹음이 끝나는 경우는 셋뿐이다.

  ① 20초 상한 도달   ② 아무 번호 누름   ③ 끊음

③으로 끝나면 2턴(본인 확인)을 할 수 없다. 통화가 이미 끝났기 때문이다.
그래서 인사말과 확인 질문 양쪽에 **"마치면 아무 번호나 눌러 주세요"** 를 넣는다.
이 안내가 없으면 어르신은 상한까지 기다리거나 끊어 버린다 — 실제로 인사 도중
끊겨서 녹음이 시작조차 못 한 통화가 있었다.

처음에는 `finishOnKey="#"` 로 우물 정자만 받았는데 **실통화에서 눌러도 넘어가지
않았다.** 통화 중에 폰을 떼고 정확히 우물 정자를 찾아 누르는 것 자체가 어렵고,
회선에 따라 DTMF 가 제대로 전달되지 않기도 한다. 그래서 아무 키나 받는다.

키가 아예 안 먹는 회선이면 `maxLength` 로만 끝난다. 그 경우 어르신이 견뎌야
하는 침묵이 그만큼 길어지므로 상한을 20초로 낮췄다. 시연장에서
`CLAWOPS_MAX_RECORD_SECONDS` 로 더 줄일 수 있다.

그래도 안 되면 **2턴을 포기하고 1턴만 쓴다** — 말하고 그냥 끊어도 녹음은
전달되므로 접수는 만들어진다. 본인 확인 단계만 사라진다.

## 2턴이 안 들리면 1턴으로 내린다

`<Record>` 의 action 응답으로 통화를 이어가는데, 그러려면 응답 전에 녹음
내려받기와 STT 가 끝나야 한다. **보내는 쪽이 얼마나 기다려 주는지 문서에 없다.**
실통화에서 확인 질문이 들리지 않은 적이 있다 — 우리 로그에는 200 으로 찍혔지만
그때는 이미 통화가 끝난 뒤였을 수 있다.

단계별 시간을 로그에 남긴다.

```
INFO:  내려받기 1.2초 · 전사 0.8초 (112000바이트)
INFO:  녹음 처리 2.1초 소요
```

이 시간이 길면 2턴을 포기한다.

```
CLAWOPS_TWO_TURN=0
```

1턴만으로도 접수카드는 나온다. 실제로 첫 통화의 한 문장에 병원·날짜·시각이
모두 들어 있었다.

    "허리 아파서 내일 송정병원으로 10시에 가야 될 것 같아"

대상자 확인은 사회복지사 확인전화에서 하면 된다 — 원래 우리 설계가 그렇다.
어르신에게 통화를 더 붙들어 두는 것보다 이쪽이 나을 수 있다.

## 아직 검증되지 않은 것

실제 통화로 확인해야 하는 것들이다. **회선을 붙이면 이것부터 재야 한다.**

1. **전화 음질에서의 인식률.** 녹음은 `WAV PCM 16bit mono 8kHz` 다. 지금
   Whisper 는 그보다 좋은 음질 기준으로 돌고 있어 인식률이 떨어질 수 있다.
   어르신 사투리까지 겹치면 더하다. 떨어지면 모델을 키우거나 ClawOps 자체
   전사(`client.calls.get_transcript()`)와 비교해야 한다.

2. **응답 시간.** 녹음 콜백에서 내려받기 + STT + 분류를 마쳐야 다음 안내가
   나간다. 그동안 어르신은 침묵을 듣는다. ClawOps 가 우리 응답을 얼마나
   기다려 주는지(타임아웃) 확인이 필요하다. 길면 `<Say>` 로 "확인 중입니다"를
   먼저 내보내는 구조로 바꿔야 한다.

3. **인사말 길이.** 지금 네 문장이다. 실제로 들어보고 줄여야 할 수 있다.

4. **`<Dial>` 전환 성공률**과 담당자가 못 받았을 때의 동작.
